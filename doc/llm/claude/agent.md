## 基本常识
1. CoT: 把一步到位的黑盒推理，变成课件中间步骤
2. ReAct: 循环 `思考 -> 行动 -> 推理`，直到最终的结束
3. Human-in-the-Loop: 在 AI 执行关键操作前，保留人类的审批权
4. Agent: LLM + Memory + Planning + ToolUse
5. Agent Harness: 提供隔离，自动化，可重复，可审计的基础设施
   * 执行日志/审计追踪/合规记录
   * 权限系统/沙箱操作/危险拦截、确认
   * 代码库索引/历史会话/跨会话持久状态/Memory
   * 执行，回滚能力
   * tool操作（read write bash edit ...）
6. Vibe Coding: 通过SDD进行规格的冻结，约束
   * 消除歧义
   * 安全需求显示化
   * 生成确定性
   * 验证基准

## 思考
1. claude code 的发展现在不仅仅局限于本地，还扩张了云业务（云上需求分析，云上代码编写， 云上代码review）
2. claude code 在模型及工具越来越强大后，对应的权限也变动也进行了调整（computer use ,  /effort , /goal ，Auto Mode模式）
3. claude code 在编码越来越强大的同时，对应的机制也应该由AI处理（/code-review代码审查，/rewind回滚，/usage用量检测）
4. AI不一定提高生成力，需要根据场景进行区分
   * 对于自己熟悉维护的代码/核心严谨业务逻辑，人类更快（开发者要花时间沟通，指挥AI需要了解项目及逻辑，开发者需要花时间审查及纠错）
   * 对于不熟悉项目或重复的原型，AI更快
5. 对于老项目的改造
   * 特征测试（有些大模型看起来是bug，但他不一定是，就算是长期运行了那么久，不应该改变他的原始行为）「记录现状」而非「修正对错」。
   * 绞杀者模式 —— 增量替换，而非推倒重来
     * 不是一下子全部替换
     * 增量的构建新功能
     * 确保特征测试可以通过
6. 当今程序员应该掌握的能力
   * 规格的定义能力
   * 价值判断能力
   * 为结果担当的能力
7. 用AI存在的问题（对抗「自动化反讽」的自我成长能力）——由于长期AI编写，逻辑实现，调试导致能力的丢失
   * 刻意练习
   * 自己深度思考
   * 指挥而不是依赖AI

## Agent
我们希望能够通过Agent和大模型这个不确定的东西变成我们能够管理、管控的系统。所以衍生出了 `OpenCode` / `Claude code` 或是 `trae`/ `codebuddy` 或是 `OpenClaw`这种Agent工具/应用。它是可以真正干活的。同时也能满足你的预期
*  `OpenCode` / `Claude code` 采用的是CLI的方式,通过TUI的方式进行交互
*  `trae`/ `codebuddy` 采用的是原生的代码编程IDE的方式
*  `OpenClaw` 采用的是通过聊天工具的方式进行交互，控制你本地的电脑/服务器

我们应该思考，借助AI工具我们如何与别人差距在哪里，解决了什么问题，创造了什么价值。他们的每一次的升级都是更加贴近人。工具其背后的设计模式才是我们需要学习的（今天A工具明天出了B工具）
* chatGPT: 成为一个良好沟通的朋友，你问他他乐于回答你，但是还是要你自己做事
* Claude Code: 成为一个会处理工作上的员工，你告诉它需要怎么做，它就会按照你的要求去完成，
* OpenClaw: 成为一个会秘书，可通过聊天工具下达命令，完成你给他的工作，目前它无法想Claude Code解决专业的问题（只有skill技能，没有其他的如hook，subAgent等）。

通过Agent我们需要思考
* 创造了什么价值
* 解决什么问题

Agent 中使用的问题
1. Agent如何把行为不可预测变成可控（通过Agent.md进行约束）
2. Agent能力复用（听过markdown文件进行管理）
3. 复杂任务（通过skills，subagent，agent teams进行优化，同时借助SDD实现任务的分析，架构的方案，任务的指定拆成细粒度的工作）

Agent 7大能力
* 感知: 获取外部内容
* 记忆: 提供连续性内容
* 推理: 思考如何处理
* 行动: 获取外部工具
* 反思: 是否处理正确，是否需要继续处理，是否已经完成
* 协作: 单agent处理不来，如果multi-agent之间协作，汇总
* 治理: 限制，记录，权限，

Agent能力的6个流转
* 链式: 从上到下的执行
* 路由: 先判断哪一类问题后再进行流转
* 并行: 统一任务的并行处理
* 编排: 中心节点复杂拆解，然后分发，汇总 （一层中心编排多个 worker）
* 循环: 直到条件停止
* 层级: 多层委派，（父节点管目标，子节点管局部，孙节点继续细分）

最怕Agent做错的事
* 代码Agent最怕看错仓库，改错文件
* 个人组手最怕身份、权限和长期记忆失控
* 多Agent最怕任务拆开后收不回来
* 沙箱执行最怕"能做事"变为"乱做事"

上下文
* 上下文信息：什么内容应该放在上下文中（过滤有用的消息放入上下文而不是无脑操作）
  * P0/P1: 直接放入Context （CLAUDE.md && tools && skill && system prompt）
  * P2: 压缩摘要放入(历史对话，背景文档,旧工具结果)
  * P3: 挂路径按需加载（代码库，文件）
* 语意压缩：信息进来后，怎么变短不丢失关键证据（当一个消息进入上下文中压缩大小对其多余消息）但是压得越多次语义丢失可能就越大
  * 把冗长的tool output 提取出重要的结果信息
  * 把旧对话合并成任务状态，比如用户意图，已做改动，已做决策等
  * 把历史对话合并成历史摘要（context压力很大时才触发）
* 渐进式发现：先把一些`目录或消息放入上下文，等真正用到时才加载
* 多模态：图片，pdf，日志 这些怎么进入上下文

## 传统的Agent与Harness
* 在早期大模型还不够强大时，需要通过Chain或RAG等框架实现Agent的功能。但是这种方式就变成了硬编码的方式（不够灵活，完成单一的任务）。在现在大模型变成一个拥有极强规划能力的CPU.它不需要规定执行的流程，只需要告诉他有什么工具，通过上下文及指令，他就可以自动进行编排及推导下一步要执行什么。
    * Chain: langchain
    * RAG: langgraph

### Harness的问题
* 由于Harness是基于大模型的，所以能力边界就变得非常的重要，通过指定工具给大模型提供手脚的同时通过middleware中间件、权限等控制大模型的行为。

### ReAct
1. 大模型适配器（可以指定不同类型的大模型，如openAI, anthropic等） 
2. tools、mcp 工具 (read, write,bash,edit)
3. 输入输出工具（飞书，本地终端） 
4. middleware中间件 (权限控制)
5. context工程 (上下文的拼装，各种markdown文件的拼装及更新)
    * 基础的提示词
    * AGENTS.md/CLAUDE.md
    * SKILL.md (metadata)
6. session 长期记忆 （过长： 只保留近期的数据，之前的可以进行总结或丢弃）
    * 两阶段ReAct中第一阶段是不用写入到长期记忆里面
    * System Prompt提示词是每次都需要传递，也不在长期记忆里面
    * tools_call与tool_result是成对出现的。同时还要保留tools_call的上一条user消息
    * 通过session_id进行隔离及持久化及加载
    * 单个消息 （过大： 超过大小时截取前后多少字节）
        * 截断后需要补充截断避免大模型认为这就是完整的数据 
7. plan模式 (生成PLAN.md)
    * 读取文件，分析需求，生成PLAN.md
    * 不进行其他的edit或write 
8. 两阶段 ReAct
9. 调用工具出错处理 （在出错的报错时添加提示词引导大模型去处理而不是直接报错停止， 不只是"发生了什么"，还要回答"接下来该试什么"）
    * 方式1: 在每个tools工具中实现
    * 方式2: 创建类一个独立处理（传入tools_name及err生成一个新的prompt_err）
10. System Reminders 机制（LLM 的注意力机制对"位置远的内容"敏感度会下降。如果所有规则都只写在对话开头的 system prompt，在长对话中 LLM 容易"忘记"。System Reminders 通过在每轮或特定时机重新注入，解决这个问题）
    * 当执行工具后，如果是失败判断当前工具失败的次数，如果超过一定的次数则加一条消息让系统不在继续执行应该重新整理思路改为其他方式执行）
    * 主动干预告诉大模型当前的重点是什么（在单轮会话中上下文过长一直还没有得到结果时提醒最初的提示词是什么）
11. 多子智能体处理（独立上下文）
12. Human-in-the-Loop

#### ReAct Main处理
LOOP处理 —— 用户输入，封装提示词上下文，调用大模型，调用工具，更新上下文，重复以上过程
* 封装提示词上下文
    * 角色
    * AGENT.md/USER.md等
    * 工具描述
    * 用户输入
* 循环处理
    * 两阶段 ReAct（带有thinking的大模型时这个两阶段是内部完成）：
        1. 阶段一（思考）：传入问题，不让模型直接执行  → 输出：任务拆解、执行步骤、工具选择计划
        2. 阶段二（执行）：思考结果 + 可用工具 → 传给模型 → 输出：tool_call（工具名+参数） 或 最终答案
           * 用户确认（Human-in-the-loop）
               * 执行工具，获取结果
               * 将工具结果回传上下文
           * 判断是否结束循环
               * 有新的 tool_call → 继续循环
               * 输出最终答案 → 退出循环

## SDD
### 软件工程的协作困境
多个开发者在各自的认知模型里，通过代码、文档。会议来同步理解，但是同步之间就存在`隐式假设`（每个人都觉得对方跟我想的是一样的）。
* 命名规范
* 架构分层
* 入参出参
* 实现方式

### SDD
规格(是合同不是文档)是第一公民，代码是规格的证明 （规格先行，规格即文档，规格测试，规格即沟通）
* 传统开发: 需求讨论 -> 前后端各自实现 ->  联调/修改 
* SDD开发: 需求讨论 -> 共写规格 -> 规格评审  -> 并行开发  -> 合约测试  -> 集成

### 规格的制定
规格的要求
1. 规格不是一次性交付的。他是一个活文档，随着代码的演进也需要进行变化
2. 不把swagger当做规格，因为常见的通过代码的注解生成这是代码先行而不是规格先行。应该使用的是proto或openAPI定义接口契约。后续在通过代码生成工具生成stub，在通过stub填充业务
3. 规格不单单是后端的制定，需要前端、移动端、第三方集成方沟通制定，讨论他们各自的规格需求

### 规格的格式
* `OpenAPI 3.2`: `REST API`规格的事实标准
* `AsyncAPI 3.0`: `事件驱动架构`规格的事实标准
* `Protocol Buffers`: `gRPC` 规格的事实标准
* `TypeSpec`: 微软推出的下一代API规格语言。可编译到OpenAPI、Protobuf、JSON Schema等多种规格

### SDD与TDD的关系
规格先行是TDD的上一层（如果双方各自写了测试之后，再发现大家的字段不一致，那一切都是徒劳）
