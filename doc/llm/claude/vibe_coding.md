# vibe coding

## 人应该做的事
1. 制定要求
    * 制定边界，制定规范，制定要求（`CLAUDE.md`）
    * 制定hook (`.claude/settings.json` / `SubAgent`) 及权限(`.claude/settings.json` / `SubAgent` / `skills`)
    * 制定流程，制定任务 (`SDD`)
2. 验收代码
    * 检查生成的是否在边界内（错误处理，异常，潜在风险）
    * 有没有遵循项目规范，风格，一致性
    * 是否能满足业务需求
    * 是否能按照你进行实现
    * 检查代码的质量

## 上下文/memory
1. 把每次重复需要告诉大模型的写入到`CLAUDE.md`/`Agent.md` 中。可以把部分提示词放到`SubAgent`或`skill`（按需加载）
2. 写入项目的大纲，命名规范，路径规范，入参出参要求，错误处理，各个路径下处理能内容。
3. memory不是一开始就能写得完美，需要一步一步的调试修改制定。
4. 制定规范时应该尽可能具体而是不是模糊的，如 "代码简洁"，"好阅读"，"结构清晰"
5. 由于上下文有限，把容易出错的写入。基本不会出错的条目不用特别提醒
6. 当一些编写限制时经常/偶尔不能拦截时，可以补充这样做的目的/场景（大模型现在的能力已具备理解场景）
7. 通过模版可以让大模型通过样例进行符合预期的生成

## 常见的AI场景
1. 程序员：代码生成 ,代码优化 ，重构 ，review
2. 运维：devops生成 (dockerfile ，makefile , jenkins ,k8s yaml)
3. 产品经理： 需求文档，代码解释文档，通过代码生成原始需求
4. 程序员/运维：线上问题排查 (CLI或 Headless)

# init初始化

## 老项目
对应老项目已经有固有的依赖、流程、代码规范等，`读取+分析`真是大模型最擅长的事，但是有可能分析或文档有误。我们并不要求生成时百分之百对，后续可以慢慢修正及调整

1. 让大模型分析整个项目生成文档
   * 架构图：给出整个项目的整体架构，此时不会显示具体的代码等层面，(产品经理、架构师等等查看，用于建立整体印象忽略细节)
   * 依赖图：给出整个项目的依赖关系，会涉及到哪个模块引用什么中间件，那个模块依赖哪个模块,(架构师、程序员、运维等，用于影响分析和排除故障)
   * 流程图：给出具体的从模块A到模块B到具体的中间件中间的流程（写代码及排查bug的人查看，用从发起到结果的整个流程，如何流转）
   * controller、service、domain等代码规范：给出实现该类时的相关样例
   * 项目接口文档、ER图 （可选）
2. 结合步骤1生成的文档生成CLAUDE.md及skill
   CLAUDE.md文件
   * 项目基本架构。使用了什么语言，同时引用文档中架构图及依赖图
   * 给出简要的流程，同时引用文档中流程图
   * 文件夹路径：每个文件夹具体存放了什么文件，主要是什么存放什么类型的代码
   * 指出生成对应的代码需要加载读取对应的代码，引用文档中代码样例
   * 给出项目中一些常见的规范要求及禁止的规范要求
     skill技能
     通过上面的上下文分析可以抽离的技能形成流水线，把常见的流程进行技能的生成
3. 本地环境的搭建
   * 项目中依赖的中间件是否需要自己本地搭建运行，如需要可根据依赖图及项目中的配置文件，依赖库选定对应的中间件及版本号。
   * 如需搭建中间件时可以让大模型生成docker-compose并执行。中间的每一步操作都记录到xxx.log文件中，该log文件对后续其他设备遇到错误时有很好地参考作用
   * 生成对应的shell命令。（如一键启动，一键关闭等功能）


## 新项目
对应新项目，由于没有历史依赖及架构代码的问题，可以从零开始。通过对话逐步确认项目基础设定，最终产出项目记忆文件

1. 与大模型讨论并分析生产CLAUDE.md文档
   * 讨论项目中使用的技术栈
   * 有什么依赖、中间件
   * 项目的架构分层
   * 给出相关的代码样例（保存到其他目录，用于引用的方式写入CLAUDE.md文档）
   * 给出项目中一些常见的规范要求及禁止的规范要求
2. 通过沟通生成skill技能
   * 把常见的流程与大模型进行沟通梳理成对应的skill工具，后续使用该skill进行生成
3. 生成shell脚本
   * 中间件搭建/云服务创建
   * docker-compose文件的编写及搭建
   * jenkins文件的编写（可选）
   * k8s文件的编写（可选）
   * 一键启动/关闭的shell

## 基础信息

### Memory文件
声明式而不是命令式的
1. 控制在500行以内，太长会稀释关键消息
2. 重要的规则放前面
3. 随着项目演进需要更新，避免过期规则
4. 每次修改需要Code Review。共同维护

组成部分
1. 项目概述： 项目是什么，做什么 
2. 技术栈： 什么语言，数据库，测试工具
3. 编码规范： 命名规范，代码风格
4. 项目结构：目录布局和职责
5. 工作流程: 提交规范，分支策略，CI/CD
6. 特殊约束: 安全要求，性能要求，合规要求


### Sub-Agents（agent = 角色 + 权限 + 任务）
子代理作用
1. 赋予不同的权限（只读，读写，bash操作）允许/禁止
2. 隔离主agent的上下文
3. 每个agent负责不同的业务（可添加不同的memory + skill）

子agent的上下文
  *子 agent 能拿到的:
    * 它自己的 system prompt(即 agent 定义里的 prompt)
    * 调用时 Agent 工具传入的 prompt 字符串(这是父→子的唯一通道)
    * 项目的 CLAUDE.md(通过 settingSources 加载)
    * 工具定义(默认继承父的,或 tools 里指定的子集)
  * 子 agent 拿不到的:
    * 父 agent 的对话历史和工具结果
    * 父 agent 的 system prompt 
    * Skills(除非在 AgentDefinition.skills 里列出)

设计模式
1. Router：       分发（主代理转发，子代理A/B/C做事）
2. Orchestrator： 拆解+汇总 —— 每个子agent做不同的事
3. Divide：       拆解+汇总 —— 每个子agent做相同的事（A看xx路径文档，B看xx2路径文档）
4. Competition：  team类型（多个子代理处理，最总辩论出一个结果）
5. supervisor：   子代理循环 —— A出来完给B，B处理完给A 


### skill
把隐形的经验变为可复用的工具手册
1. 允许怎么工具（权限）
2. 什么时候触发这个技能
3. 这个技能的操作步骤 —— 执行步骤，获取文档(可选)，执行脚本(可选)，注意事项，输出内容，最终校验

# 新需求改造
1. 让AI分析需求
   * 与AI讨论需求，澄清需求点（达成清晰的目标什么做什么不做，功能点是什么）生成`prd.md文档`
   * 有什么功能，定义什么字段，有什么交互，流程是怎样的
2. 生成规格及任务文档
   * 获取/创建 得到该业务最新的业务更新`memory.md` 文件，逻辑即流程图等（原先项目中的逻辑(前端/后端)）
   * 根据`memory.md`文档 + `prd.md文档` + spec模版生成`spec.md文件`
   * 根据需求整理本次的需要改动到的地方及不需要改动的地方， 拼接到`spec.md文件`
   * 根据需求点中需要的改造整理一份流程图, 拼接到spec.md 文件
   * 根据上面的改造点及流程图，新旧功能对比分析一下改造的影响范围， 拼接到`spec.md文件` （编写对应的测试用例）
   * 根据上面的改造点，流程图，影响范围，生成改造计划及方案 ，生成到`plan.md文件`
   * 开启独立上下文根据 `spec.md文件` 及 `plan.md文件` 分析是否有问题
   * 功能过多可以根据 `plan.md 文件` 拆分成几个`task.md文档`
3. 代码生成
   * 生成/运行原有代码的测试用例
   * 依次生成domain/repository/service/DTO等
   * 生成新需求的测试用例（满足原有功能的可以过，新功能的也可以过）
   * 运行新老测试用例
   * 更新`memory.md`文档
